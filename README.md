# Build-a-Date

Make a deck of date ideas, share the link, and whoever you send it to picks the cards they like into a plan.

- Accounts use **passkeys**, with no passwords. You sign up with an email link, then add a passkey. You can always sign in with an email link instead, whether you skipped the passkey or lost it, and add a new one from Settings.
- Each account can have any number of **decks**. A new deck starts empty or with about 30 general suggestions.
- Anyone with a deck's share link can **build a plan** without an account. Pressing Done saves the plan under its own link (`/p/…`), and it shows up on the deck owner's page.
- Someone with the link can also **ask to help edit** the deck. The owner is emailed, and once they accept, the deck shows up under Shared decks on the other person's account. See [docs/deck-sharing.md](docs/deck-sharing.md).

## Stack

[Next.js](https://nextjs.org) (App Router), deployed to [Cloudflare Workers](https://developers.cloudflare.com/workers/) with [OpenNext](https://opennext.js.org/cloudflare). Data lives in [D1](https://developers.cloudflare.com/d1/) through [Drizzle](https://orm.drizzle.team). [Better Auth](https://www.better-auth.com) handles accounts (passkey and magic-link plugins), and [Resend](https://resend.com) sends the email. [Biome](https://biomejs.dev) lints and formats, [Vitest](https://vitest.dev) runs the unit tests, and [Playwright](https://playwright.dev) runs the end-to-end tests.

| Path | What's there |
| --- | --- |
| `src/app/(app)` | Signed-in pages and auth pages, which share the site header, including `/d/[shareId]/request` (asking for edit access) |
| `src/app/(public)` | The pages anyone with a link sees: `/d/[shareId]` (build a plan) and `/p/[planId]` (a saved plan) |
| `src/lib/decks.ts` | All deck, card and plan queries. Each takes a `db`, so the tests can pass in SQLite |
| `src/lib/actions/` | Server actions: auth and validation, then a call into `decks.ts` |
| `src/lib/auth-config.ts` | Better Auth setup, shared by the app (`auth.ts`) and the schema generator (`auth-cli.ts`) |
| `src/db/` | Drizzle schema. `auth-schema.ts` is generated, so don't edit it by hand |
| `drizzle/` | SQL migrations, generated by drizzle-kit and applied by wrangler |

## Local development

Needs Node 22 or later.

```sh
npm install
cp .dev.vars.example .dev.vars   # then set BETTER_AUTH_SECRET: openssl rand -base64 32
npm run db:migrate:local
npm run dev                      # http://localhost:3000
```

With `RESEND_API_KEY` left empty, sign-in emails aren't sent. The link is printed in the terminal instead, and `GET /api/dev/outbox` returns it. Setting `EMAIL_DELIVERY=outbox` does the same even when a key is set. Both only work on localhost. Open the app at `http://localhost:3000` rather than `127.0.0.1` or a network address: passkeys and Better Auth are tied to the origin in `BETTER_AUTH_URL`, and Next's dev server blocks its scripts on other hosts.

`npm run dev` runs Next's dev server in Node, with D1 and the other bindings provided locally. `npm run preview` builds the app and serves it with workerd, the runtime Cloudflare uses, which catches anything that only breaks on Workers.

### Changing the database

1. Edit `src/db/schema.ts`. After changing Better Auth plugins, run `npm run auth:generate` to regenerate `src/db/auth-schema.ts`.
2. `npm run db:generate` writes a migration to `drizzle/`.
3. `npm run db:migrate:local` applies it locally.

### Checks

```sh
npm run lint        # Biome (npm run format to fix)
npm run typecheck
npm test            # Vitest
npm run test:e2e    # Playwright, against an OpenNext build in workerd
E2E_TARGET=dev npm run test:e2e   # the same, against `next dev` (faster)
```

Run `npx playwright install chromium` once before the first e2e run.

The e2e tests start their own server on port 3100, so they can run alongside your dev server without touching it. That server uses the `e2e` wrangler environment, so it reads `.dev.vars.e2e` instead of `.dev.vars` and keeps its own local database in `.wrangler/e2e`. Emails go to the in-memory outbox (`EMAIL_DELIVERY=outbox`) and never to Resend; the unit tests stub `fetch` for the same reason. Passkeys use Chrome's virtual authenticator. Each browser in a test sends its own `cf-connecting-ip`, so sign-in rate limits apply per visitor, as they do on Cloudflare. One spec runs with JavaScript turned off, to check the email and sign-out forms work before the page hydrates.

## Deploying

One-time setup:

1. `npx wrangler d1 create build-a-date`, then put the returned `database_id` in `wrangler.jsonc`.
2. In Resend, verify the domain you send from, and set `EMAIL_FROM` in `wrangler.jsonc` to match.
3. Set the secrets:
   ```sh
   openssl rand -base64 32 | npx wrangler secret put BETTER_AUTH_SECRET
   npx wrangler secret put RESEND_API_KEY
   ```
4. Check `BETTER_AUTH_URL` in `wrangler.jsonc` is the public URL. Passkeys are tied to its hostname.

Then, for every deploy:

```sh
npm run db:migrate:remote
npm run deploy
```

### Bringing over the original deck

The deck from before accounts existed is still in `src/data/cards.json`. Once you've signed up, import it as a deck you own:

```sh
node scripts/import-cards.ts you@example.com "Melbourne dates" > import.sql
npx wrangler d1 execute build-a-date --remote --file import.sql
```
